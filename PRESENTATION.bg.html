2 мин
Организационният проблем

Един SPA спира да скалира при 3-ти екип

  • Един екип, една codebase, един CI, един on-call — нормално.
  • Три екипа, които ship-ват един SPA — merge-ите болят, release-ите се coupl-ват, bug в Billing блокира release на Open Account.
  • Микро фронтендите разменят build-time координация за runtime композиция.
Мотивацията е организационна, не техническа. Под 3 екипа → добре структурираният монолит печели.
Устоявай на импулса да го представиш като perf печалба или migration път. Това е pattern за автономност на екипа.

2 мин
Механизмът

Module Federation в една картина

Всеки remote декларира какво expose-ва:

// mfe-trading/vite.config.ts
federation({
  name: "mfe_trading",
  filename: "remoteEntry.js",
  exposes: {
    "./TradingPage":    "./src/pages/TradingPage",
    "./PortfolioWidget":"./src/widgets/PortfolioWidget",
  },
  shared: ["react", "react-dom",
           "@tanstack/react-query"],
})

Shell-ът ги консумира по време на runtime:

// platform-shell/vite.config.ts
federation({
  name: "platform_shell",
  remotes: {
    mfe_billing:      "http://…:5175/assets/remoteEntry.js",
    mfe_open_account: "http://…:5174/assets/remoteEntry.js",
    mfe_trading:      "http://…:5176/assets/remoteEntry.js",
  },
  shared: ["react", "react-dom",
           "@tanstack/react-query"],
})
// platform-shell/src/pages/DashboardPage.tsx
const PortfolioWidget = lazy(() => import("mfe_trading/PortfolioWidget"));

Това е цялата интеграция — три remote-а, нула споделен изходен код.

2 мин
Контрактът

Какво пресича границата на екипа

  1. Името на exposed модула + подписа на default-експорта (компонент).
  2. Shared singleton-и декларирани в shared: списъка на federation.
  3. Runtime контракти, които надграждаме — auth SDK, CSS токени, accountId. Явни, минимални.

Без shared npm пакет. Без shared type import-и по време на build. Всеки MFE регенерира собствения си API клиент от един и същ Swagger.

Когато Billing прави rebuild, никой друг не rebuild-ва. Когато Billing deploy-ва, никой друг не deploy-ва. Това е цялото обещание.
1.5 мин
Непосредствени

Shared singleton-и

shared: ["react", "react-dom", "@tanstack/react-query"]
  • React / React DOM — два инстанса чупят hooks-овете. Непосредствено.
  • @tanstack/react-query — един QueryClient през shell + всички MFE-та. Това е нашият cross-MFE messaging слой.

Плати invoice в mfe-billing → invalidate-ва billingKeys.all → OutstandingBalanceWidget на Dashboard-а refetch-ва. Без event bus, без prop drilling.

Shared cache е най-евтиният event bus, който някога ще притежавате.

Отплатата

Dashboard — runtime композиция на екрана

  • 4 плочки, 4 team badge-а, 3 lazy-load-нати remote-а.
  • Източник: DashboardPage.tsx, три lazy(() => import(…)) реда.
  • Всеки widget чете същия token, пише в същия cache.
const OutstandingBalanceWidget = lazy(() => import("mfe_billing/OutstandingBalanceWidget"));
const OnboardingProgressWidget = lazy(() => import("mfe_open_account/OnboardingProgressWidget"));
const PortfolioWidget          = lazy(() => import("mfe_trading/PortfolioWidget"));

На живо: плати invoice → outstanding balance пада. Без wiring.

Превключи към браузъра за ~30 секунди. Покажи dashboard-а, кликни pay, покажи как widget-ът update-ва.
1.5 мин
Втори pattern за композиция

Slot композиция: MFE резервира място за друг екип

Dashboard = shell композира нова surface. Тук обратното: собствената страница на екип резервира ReactNode slot; shell го пълни.

// Страницата на Open Account екипа
interface Props { billingSlot?: ReactNode; }
export default function OpenAccountPage(
  { billingSlot }: Props = {}
) {
  return (
    <div>
      …
      {billingSlot && <aside>{billingSlot}</aside>}
      …
    </div>
  );
}
// Platform Core композира в shell-а
<OpenAccountPage
  billingSlot={
    <MfeBoundary label="Outstanding balance">
      <OutstandingBalanceWidget />
    </MfeBoundary>
  }
/>
  • mfe-open-account има нула import-а от mfe_billing.
  • Същият контракт: име + подпис на компонента — подписът сега включва ReactNode prop.
  • Същият shared QueryClient: плати invoice на /billing → widget-ът в /accounts refetch-ва.
  • Вложеният MfeBoundary = Billing outage показва widget-размер грешка; onboarding pipeline-ът продължава да работи.
Два pattern-а, същите примитиви. Shell-ът е единственото място, на което е позволено да знае за два екипа едновременно.
На живо: navigate до /accounts, покажи "Firm billing health" панела; после /billing, плати invoice; после обратно — slot-ът е update-нал. Ако running long, този slide е първият за отрязване — point-ът му е subsumed от slide 7 ако аудиторията е вече убедена.
2.5 мин
Където екипите реално се coupl-ват

Auth: shell-owned, runtime SDK контракт

Три опции; избрахме #3.

  1. Всеки MFE със собствен login → UX кошмар.
  2. Shared auth пакет → връща build coupling.
  3. Shell притежава auth, публикува runtime SDK към remote-ите.
// platform-shell/src/auth/platformSdk.ts
export interface PlatformSdk {
  getToken(): string | null;
}
window.__AMP_PLATFORM__ = {
  getToken: () => currentToken,
};
// mfe-trading/src/api/index.ts
http.interceptors.request.use((config) => {
  const sdk = window.__AMP_PLATFORM__;
  const token = sdk?.getToken?.() ?? null;
  if (token) config.headers.set(
    "Authorization", `Bearer ${token}`);
  return config;
});

При 401 MFE-то fire-ва amp:auth-expired на window; shell-ът чува → форсира logout.
Cross-team контракт = един interface shape + едно име на event. Дублиран inline във всеки MFE.

Production upgrade: federation-exposed SDK или import-map модул с typed stubs. Window bag-ът учи правилния mental model.
1.5 мин
Дизайн система без design-system пакет

Theme: CSS токени като имплицитен контракт

/* Дефинирани от shell-а на <html data-theme="dark"> */
[data-theme="dark"] {
  --bg: #0f1117;
  --text: #e8ebf2;
  --border: #2e3240;
  /* … */
}
  • CSS модулите на всеки MFE реферират var(--bg), var(--text) — не знаят кой ги е задал.
  • Shell-ът пише data-theme на <html>; remote-ите наследяват безплатно.
  • Всеки MFE дефинира собствени fallback токени в собствения си index.css, така че standalone работи.
Shell-owned CSS променливите = design-system контракт без design-system пакет. Същата decoupling история.
2 мин
Cross-domain данни

accountId като join key

api/src/domains/ ├── auth/ (Platform Core) ├── billing/ (Billing) — invoice-и tag-нати по accountId ├── accounts/ (Open Account) — притежава identity, KYC, product type └── trading/ (Trading) — притежава positions + cash, keyed по accountId
  • Купи AAPL на acc_verified_1 → Trading debit-ва собствения си Map<accountId, number>.
  • Trading не пита Accounts дали съществува — lazy-init на $1,000,000.
  • Invoice-ите на Billing за същия акаунт са незасегнати.
Всеки екип притежава собствения си срез на това какво е "акаунт". Споделената конвенция е един string.
1.5 мин
Контракти за типове

Един Swagger, четири генерирани клиента

api/src/swagger.ts (source of truth) │ ▼ tsx generateSwagger.ts api/swagger.json │ ├──► platform-shell/src/api/generated/ (само auth) ├──► mfe-billing/src/api/generated/ ├──► mfe-open-account/src/api/generated/ └──► mfe-trading/src/api/generated/
  • Генерацията се случва per-пакет — без shared types пакет.
  • Trading чупи своя endpoint → само Trading не typecheck-ва.
  • Всеки MFE wrap-ва генерирания клиент в api/index.ts + query-key factory.
Контрактите пътуват чрез регенерация, не чрез import-и. Това е дисциплината.
1 мин
Остър ръб

CSS изолация в remote-ите

Federation плъгинът на Vite не зарежда CSS файлове от remote-и. Без намеса widget-ите mount-ват нестилизирани в продукция.

// vite.config.ts на всеки MFE
plugins: [
  cssInjectedByJsPlugin(),  // inlin-ва CSS в JS bundle-а
  federation({ … }),
]
  • Плюс isolation: isolate на root контейнера на всеки MFE, така че стиловете да останат scope-нати.
  • Плюс CSS Modules, така че имената на клас са hash-нати.
Пропуснеш ли това, federated страниците ти рендират нестилизирани в продукция. Тествай composed режима рано.
1.5 мин
Как екипът реално работи

Три dev режима на MFE

  1. Standalone с HMR — npm run dev:trading:standalone. Vite dev, собствен QueryClient, собствен Router. Team-local итерация, нула външни зависимости.
  2. Built preview — npm run dev:trading. vite preview сервира dist/. Нужно, защото shell-ът консумира remoteEntry.js, който съществува само след vite build.
  3. Консумиран от shell-а — lazy(() => import("mfe_trading/…")) на shell-а взима remote-а; MFE-то ползва provider-ите на shell-а.
Standalone е как държиш екипа unblocked. Никога не ти трябват другите три процеса, за да оправиш bug.
1.5 мин
Организационната печалба

Deploy независимост (blast radius)

  • Убий процеса mfe-billing → widget показва error state през <MfeBoundary>. Всичко друго работи. Restart → widget се връща.
  • Три различни CI pipeline-а, три различни release cadence-а.
  • Лош deploy на Billing не чупи Trading.
  • Всеки remoteEntry.js може да живее на собствен CDN със собствена версия.
Това е най-голямата единична организационна печалба. По-малък blast radius → повече deploy-и → по-бързи екипи.
Жив момент: спри процеса mfe-billing в терминала, refresh на dashboard-а, покажи error boundary-то.

Чиста граница

Shell притежава platform concerns

Shell прави

  • Routing & навигация
  • Auth (login, session, ProtectedRoute)
  • Theme (data-theme, токени, toggle)
  • Layout (sidebar, user card, logout)
  • Error boundaries за remote-и
  • Platform SDK на window

Shell НЕ прави

  • Fetch на Billing / Accounts / Trading данни
  • Знае вътрешни компоненти на MFE
  • Знае какво е position или invoice
  • Притежава team-specific бизнес логика

Честният slide

Компромиси

Печелите

  • Автономност на екипа (dev, build, deploy, on-call)
  • Малък blast radius при грешки
  • Независим tech избор в рамките на shared-singleton-ите
  • Паралелна скорост: 3 екипа ship-ват едновременно

Плащате

  • Един React през remote-ите — upgrade-ите координират
  • CSS изолацията е ръчна
  • Runtime композиция → по-бавен first paint
  • Дисциплина за контракти нужна; хора, не инструменти, enforce-ват
  • Shell-ът е ново нещо за владеене
  • Debugging пресича 3 репа
Не е безплатно. Ако отговорът на "колко екипа ship-ват тук" е 1-2, добре модуляризиран монолит го бие.

Anti-препоръка

Кога НЕ да се прави това

  • Под ~3 ship-ващи екипа.
  • Една кохерентна продуктова surface, която се променя като цяло.
  • Ops екипът не може да работи 3 независими CI/CD pipeline-а.
  • Не можеш да се ангажираш с координация на версиите на React / core lib-и.
  • Performance бюджетът не може да абсорбира цената на runtime-композицията.
Добре структуриран монолит с ясни feature folder-и често е правилният отговор. Не микро-фронтенд-ирай пътя си към distributed монолит.
1 мин
Рекап

Какво покрихме

  1. Граница екип → пакет (mfe-<domain>).
  2. Module Federation: remote-и + exposed модули + shared singleton-и.
  3. Cross-team контракт = име + подпис. Нищо друго.
  4. Два composition pattern-а: orchestration (Dashboard) + slot композиция (OpenAccountPage.billingSlot).
  5. Cross-cutting concerns през runtime контракти: auth (window SDK), theme (CSS vars), данни (accountId).
  6. Per-пакет type generation — decoupled контракти.
  7. Три dev режима, три deploy режима.
  8. Компромиси: автономност ↔ координация.

Обичайна подготовка: • Защо MF vs iframes? Shared React, shared cache, единична SPA навигация, без sandbox overhead. • Защо не Nx с build-time import-и? Remote URL-ите могат да бъдат versioned (/v2/remoteEntry.js); manifest-ите решават.
