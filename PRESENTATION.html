Micro Frontends in practice

What we chose, what we skipped, and what it cost.

4 teams · 4 packages · Module Federation · ~30 min + Q&A

Open tabs before starting: http://localhost:5173, the repo in the editor, a terminal. Set expectations: this isn't theory, every slide maps to a real file in the repo.
2 min
The organisational problem

A single SPA stops scaling at team-3

  • One team, one codebase, one CI, one on-call — fine.
  • Three teams shipping the same SPA — merges hurt, releases couple, Billing's bug blocks Open Account's release.
  • Micro frontends trade build-time coordination for runtime composition.
The motivation is organisational, not technical. Under 3 teams → well-structured monolith wins.
Resist the urge to pitch this as a perf win or a migration path. It's a team-autonomy pattern.

Definition check

What a micro frontend is (and isn't)

It ISIt ISN'T
A runtime composition modelA way to avoid npm dependencies
An ownership boundary (team → package)A performance optimisation
Independent build + deploy per sliceA rewrite excuse
A team-autonomy enablerFree — you pay in coordination
Iframes, Web Components, Module Federation, import-maps — those are mechanisms. The pattern is team autonomy with a shared surface.

The mechanism

Module Federation in one picture

Each remote declares what it exposes:

// mfe-trading/vite.config.ts
federation({
  name: "mfe_trading",
  filename: "remoteEntry.js",
  exposes: {
    "./TradingPage":    "./src/pages/TradingPage",
    "./PortfolioWidget":"./src/widgets/PortfolioWidget",
  },
  shared: ["react", "react-dom",
           "@tanstack/react-query"],
})

Shell consumes them at runtime:

// platform-shell/vite.config.ts
federation({
  name: "platform_shell",
  remotes: {
    mfe_billing:      "http://…:5175/assets/remoteEntry.js",
    mfe_open_account: "http://…:5174/assets/remoteEntry.js",
    mfe_trading:      "http://…:5176/assets/remoteEntry.js",
  },
  shared: ["react", "react-dom",
           "@tanstack/react-query"],
})
// platform-shell/src/pages/DashboardPage.tsx
const PortfolioWidget = lazy(() => import("mfe_trading/PortfolioWidget"));

That's the entire integration — three remotes, no shared source code.

2 min
The contract

What crosses the team boundary

  1. The exposed module name + its default-export component signature.
  2. Shared singletons declared in federation's shared: list.
  3. Runtime contracts we build on top — auth SDK, CSS tokens, accountId. Explicit, minimal.

No shared npm package. No shared type imports at build time. Every MFE regenerates its own API client from the same Swagger.

When Billing rebuilds, nobody else rebuilds. When Billing deploys, nobody else deploys. That's the whole promise.

Non-negotiables

Shared singletons

shared: ["react", "react-dom", "@tanstack/react-query"]
  • React / React DOM — two instances break hooks. Non-negotiable.
  • @tanstack/react-query — one QueryClient across shell + all MFEs. This is our cross-MFE messaging layer.

Pay an invoice in mfe-billing → invalidates billingKeys.all → OutstandingBalanceWidget on the Dashboard refetches. No event bus, no prop drilling.

Shared cache is the cheapest event bus you will ever own.

Where teams really couple

Auth: shell-owned, runtime SDK contract

Three options; we picked #3.

  1. Each MFE does its own login → UX nightmare.
  2. Shared auth package → reintroduces build coupling.
  3. Shell owns auth, publishes a runtime SDK to remotes.
// platform-shell/src/auth/platformSdk.ts
export interface PlatformSdk {
  getToken(): string | null;
}
window.__AMP_PLATFORM__ = {
  getToken: () => currentToken,
};
// mfe-trading/src/api/index.ts
http.interceptors.request.use((config) => {
  const sdk = window.__AMP_PLATFORM__;
  const token = sdk?.getToken?.() ?? null;
  if (token) config.headers.set(
    "Authorization", `Bearer ${token}`);
  return config;
});

On 401 the MFE fires amp:auth-expired on window; shell listens → forces logout.
Cross-team contract = one interface shape + one event name. Duplicated inline in each MFE.

Production upgrade: federation-exposed SDK or import-map module with typed stubs. Window bag teaches the right mental model.
1.5 min
Design system without a design-system package

Theme: CSS tokens as implicit contract

/* Defined by the shell on <html data-theme="dark"> */
[data-theme="dark"] {
  --bg: #0f1117;
  --text: #e8ebf2;
  --border: #2e3240;
  /* … */
}
  • Each MFE's CSS modules reference var(--bg), var(--text) — they don't know who set them.
  • Shell writes data-theme on <html>; remotes inherit for free.
  • Each MFE defines fallback tokens in its own index.css so standalone still works.
Shell-owned CSS variables = design-system contract without a design-system package. Same decoupling story.

Cross-domain data

The accountId join key

api/src/domains/ ├── auth/ (Platform Core) ├── billing/ (Billing) — invoices tagged by accountId ├── accounts/ (Open Account) — owns identity, KYC, product type └── trading/ (Trading) — owns positions + cash, keyed by accountId
  • Buy AAPL on acc_verified_1 → Trading debits its own Map<accountId, number>.
  • Trading doesn't ask Accounts if it exists — lazy-init to $1,000,000.
  • Billing's invoices for the same account are untouched.
Each team owns its slice of what "an account" is. The shared convention is one string.
1.5 min
Type contracts

One Swagger, four generated clients

api/src/swagger.ts (source of truth) │ ▼ tsx generateSwagger.ts api/swagger.json │ ├──► platform-shell/src/api/generated/ (auth only) ├──► mfe-billing/src/api/generated/ ├──► mfe-open-account/src/api/generated/ └──► mfe-trading/src/api/generated/
  • Generation happens per package — no shared types package.
  • Trading breaks its endpoint → only Trading fails to typecheck.
  • Each MFE wraps the generated client in api/index.ts + a query-key factory.
Contracts travel via regeneration, not via imports. That's the discipline.
1 min
Sharp edge

CSS isolation in remotes

Vite's federation plugin does not load CSS files from remotes. Without intervention, widgets mount unstyled in production.

// each MFE's vite.config.ts
plugins: [
  cssInjectedByJsPlugin(),  // inlines CSS into the JS bundle
  federation({ … }),
]
  • Plus isolation: isolate on each MFE's root container so styles stay scoped.
  • Plus CSS Modules so class names are hashed.
Miss this and your federated pages render unstyled in production. Test the composed mode early.
1.5 min
How the team actually works

Three dev modes per MFE

  1. Standalone with HMR — npm run dev:trading:standalone. Vite dev, own QueryClient, own Router. Team-local iteration, zero external deps.
  2. Built preview — npm run dev:trading. vite preview serving dist/. Needed because the shell consumes remoteEntry.js, which only exists after vite build.
  3. Consumed by shell — shell's lazy(() => import("mfe_trading/…")) pulls the remote; MFE uses shell's providers.
Standalone is how you keep the team unblocked. You never need the other three processes to fix your bug.
1.5 min
The organisational win

Deploy independence (blast radius)

  • Kill the mfe-billing process → widget shows an error state via <MfeBoundary>. Everything else works. Restart → widget comes back.
  • Three different CI pipelines, three different release cadences.
  • Billing's bad deploy doesn't break Trading.
  • Each remoteEntry.js can live on its own CDN with its own versioning.
This is the biggest single organisational win. Smaller blast radius → more deploys → faster teams.
Live moment: stop the mfe-billing process in the terminal, refresh the dashboard, point at the error boundary.

Clean seam

Shell owns platform concerns

Shell does

  • Routing & navigation
  • Auth (login, session, ProtectedRoute)
  • Theme (data-theme, tokens, toggle)
  • Layout (sidebar, user card, logout)
  • Error boundaries for remotes
  • Platform SDK on window

Shell does NOT

  • Fetch Billing / Accounts / Trading data
  • Know any MFE's internal components
  • Know what a position or invoice is
  • Own team-specific business logic

The honest slide

Trade-offs

You gain

  • Team autonomy (dev, build, deploy, on-call)
  • Small blast radius on failures
  • Independent tech choices within shared-singletons
  • Parallel velocity: 3 teams ship simultaneously

You pay

  • One React across remotes — upgrades coordinate
  • CSS isolation is manual
  • Runtime composition → slower first paint
  • Contract discipline needed; humans, not tools, enforce it
  • Shell is a new thing to own
  • Debugging crosses 3 repos
Not free. If your answer to "how many teams ship here" is 1-2, a well-modularised monolith beats this.

1 min
Anti-recommendation

When NOT to do this

  • Fewer than ~3 shipping teams.
  • One cohesive product surface that changes as a whole.
  • Ops team can't run 3 independent CI/CD pipelines.
  • Can't commit to version-coordination on React / core libs.
  • Performance budget can't absorb runtime-composition cost.
A well-structured monolith with clear feature folders is often the right answer. Don't micro-frontend your way into a distributed monolith.
